## Commands

- `npm run typecheck`: `tsc` over `src/` and `test/`, no emit
- `npm test`: the whole Vitest suite; `npx vitest run test/<file>.test.ts` for one file
- `npm run conformance -- run <adapter>` / `-- matrix`: run the conformance suite on this machine and record the result, or render the support matrix from the recorded results (see below)
- `npm run build`: compile `src/` to `dist/` (needed only for `bin/ahp.mjs`; also the `prepare` script, so `npm install -g github:Mohaned178/agent-handoff-protocol` builds on install, and `ahp` with no command prints a getting-started guide)
- `npm run schemas`: regenerate `schemas/*.json` (the published JSON Schemas) from the Zod schemas in `src/protocol/`; a test fails if they are stale
- `node src/cli/bin.ts <command>`: run the CLI from source without building

## Code layout

One package, ESM, Node ≥ 24 type stripping: imports use `.ts` extensions, and `tsc` rewrites them on build, so use only erasable TypeScript syntax (no enums, namespaces or parameter properties). Modules under `src/`: `protocol` (Zod schemas and JSON Schema generation for handoffs, types, closed enumerations and state unions), `ledger` (hash-chained append-only JSONL, single-writer lock, replay), `adapters` (contract, mock, claude-code, codex, opencode, the `acp` client with the permission answers and tool-call log OpenCode uses, and the `prompt.ts` and `output-schema.ts` the tool adapters share), `process` (the shared process layer: executable resolution, launch, process-tree termination), `runtime` (worktrees, snapshots, verification, run executor, approval decisions), `sdk` (public run API), `conformance` (the adapter conformance suite, result files and the support matrix), `doctor` (`ahp doctor` and `ahp init`), `evaluation` (tasks, freezing, conditions, validators, trials, report; its ledger events are its own, not the run protocol's), `cli`. `src/index.ts` is the public SDK entry. `bin/ahp.mjs` checks the Node version, then loads `dist/cli/bin.js`. `schemas/` holds the published JSON Schemas and `scripts/` the script that generates them.

Handoff schemas are Zod (`src/protocol/handoff.ts`); rejection reasons and handoff states are `as const` arrays shared by the schema and the code, so adding one is a protocol change. A step's workspace starts from the previous step's passing snapshot commit, and a handoff's artifact hashes are SHA-256 over blobs read from that commit (`src/runtime/artifacts.ts`), never from a working tree (ADR 0005). An adapter reports a step's output fields through `AttemptExit.reportedOutput`; they are an agent claim that verification checks, and never files in the workspace. Every agent is started through `src/process`: `resolveExecutable` finds the real file on PATH (on Windows with PATHEXT; an npm `.cmd` shim is read for its entry point, which `process.execPath` runs, and any other `.cmd`/`.bat` is refused), and `launch` starts it with execa, `shell: false`, the prompt on stdin, and `PWD` set to `cwd` (a tool such as OpenCode that follows the inherited `PWD` would otherwise work in the directory AHP was started from; `launch` only adds variables, never removes one). execa itself hands any Windows file it cannot resolve to an `.exe` to `cmd.exe`, so `launch` refuses anything but an existing `.exe`/`.com` there. `LaunchOptions.transcript` keeps the raw transcript: what is sent to stdin (`input`, or each write to a duplex process's `stdin`, recorded by wrapping `write` on the process's own stream) and what stdout printed (execa's `stdout: ['pipe', { file }]`, so the file is complete once `exited` settles and the caller still reads the stream), in two files the runtime owns (`transcriptPaths`: `<runs>/<run>/transcripts/<attempt>.{in,out}.txt`, passed as `AttemptInput.transcript` and on by every adapter); stderr stays ignored (ticket 18, decision 2), and a transcript that cannot be made never fails an attempt. Agents run in their own process group on Linux and macOS (SIGTERM, grace, SIGKILL to the group), and share AHP's console on Windows, where a cancel is `taskkill /T /F` over the tree read from parent PIDs and creation times (PowerShell CIM). AHP-created worktrees get `core.longpaths` through git's per-worktree config, which turns on `extensions.worktreeConfig` in the repository (see `src/runtime/workspace.ts`).

The executor is a loop over replayed state: `drive` (`src/runtime/run.ts`) reads the next action from the state derived so far and records at least one event per turn, so any process can pick a run up from its ledger (`resumeRun` and `recoverAttempt` in `src/runtime/resume.ts` call the same `drive`). Add behaviour there as a case of "state → next action", never as flow held in memory. A cancel is recorded first (`run_cancel_requested`), so a run picked up after a crash goes on cancelling: from then on no agent is dispatched, an unknown attempt waits for a person whatever its step's policy, and anything else ends the step `cancelled`. A running agent is stopped inside `executeAttempt`, under `attempt_cancelling`, and is `cancelled` only once `StartedAttempt.cancel` confirms its tree gone after something was sent to it; an agent found already gone keeps its own exit, and an unconfirmed kill makes it `unknown (unconfirmed_kill)`. On Windows a console Ctrl+C reaches the agent as well as AHP, so a process that fails there waits 250 ms for the cancel (`cancelledAround`, `src/runtime/cancel.ts`) before its failure is believed. Waits during a cancel go through the `Clock` (`sleep(ms, signal)`). An attempt with a `dispatching` record and no end is `unknown` and never dispatched again: it gets a recovery report, then its step's `recovery` policy or a person (`ahp recover <attempt> --policy adopt|abort`) decides, and no new agent ever follows it: an adopted workspace that fails ends the step. A review step (`review: { sendBackTo }`, which must name the step immediately before it) requires `verdict` and `findings` on top of its listed output fields (`requiredOutputFieldsOf`, `src/protocol/review.ts`), and a verdict that is neither `approved` nor `changes_requested` fails verification (`review_verdict` evidence). When a passing review asks for changes, `concludeAttempt` records `step_sent_back` if the preceding step still has retry budget (`decideAfterFailure` as `verification_failed`, no reroute), else it fails the review step as `verification_failed`. Replay applies the event: the preceding step goes `succeeded → ready` and spends `retryUsage.retries`, its sent-back attempt gets `sentBack` and a `retry` with change `evidence`, so `advanceReadyStep` issues the next revision (evidence `review_findings`) through the path a failed verification uses, and the review step goes back to `blocked`. Its handoff is rebuilt from the new sender (`handsOnLatestResult`), never reused. An approval gate (`approval: {}`, a `WorkflowStepDefinition` beside the agent-step `StepDefinition`; `StepView.kind` is `agent`, `review`, `approval_gate` or `external_action`, which replay needs to apply the gate's rules) has no handoff or attempt and must follow an agent step; a step after a gate receives the result of the agent step before it (`senderIndex`, `src/runtime/run.ts`). With the step before it succeeded, `advanceGate` records `approval_requested` (the verified attempt, its snapshot and the changed paths against the run's base commit), the run goes `waiting_approval` and `drive` returns, so the process exits with exit code 4. `decideApproval` (`src/runtime/approval.ts`, behind `approveStep`/`rejectStep` and `ahp approve`/`ahp reject`) refuses before the lock, takes it as `recoverAttempt` does, re-checks, then records `run_resumed` and `approval_decided` (user and time) and calls `drive`, which finds the decision: an approval ends the gate `succeeded`; a rejection records `approval_sent_back` (the same send-back as a review's, spending the preceding step's `verification_failed` retry, evidence `approval_rejected` with the reason) or, with that budget spent, fails the gate as `verification_failed`. `inspectRun` reads the diff from the pinned snapshot commit (`pendingApprovalOf`), never a worktree. An external-action step (`action: { kind: push_branch | open_pr | merge_pr, ... }`, `isExternalAction`; `StepView.kind` `external_action`, `StepView.action`) follows a gate with nothing but external actions between them (validation), publishes the commit that gate approved (replay checks the intent against it) and has no handoff or attempt; steps after it receive the agent step's result as after a gate. `advanceExternalAction` (`src/runtime/external.ts`) records `external_action_intended` (the target: defaults filled, gate, approved commit), then in one turn looks at the remote (`external_action_checked`, `done` when it is already so) and performs it only when not done (`external_action_performed`); a failure is checked again before `external_action_failed`, which ends the step as `external_action_failed`, never retried. A run picked up with an intent and no outcome checks again, so nothing is done twice; after a cancel an action under way is checked, never performed. A push is `git push <remote> <commit>:refs/heads/<branch>`, never forced, with `GIT_TERMINAL_PROMPT=0`; pull requests go through a `PullRequestProvider` (`find`, `open`, `merge`; `src/runtime/pull-requests.ts`), whose default `githubCli()` runs `gh` with `--repo` from the remote's URL and merges with `--match-head-commit`; tests pass `fakePullRequests()` (`test/helpers/external.ts`) as `pullRequests`, `test/pull-requests.test.ts` runs `githubCli()` against a fake `gh` (`test/helpers/fake-gh.ts`), and real `gh` never runs in a test. `verifyAttempt` compares the attempt's `before`/`after` ref snapshots: any change is `forbidden_external_action_detected` evidence, which fails verification without running the command and is retried with the changed refs as handoff evidence. Failure handling is `classifyAttempt` and `decideAfterFailure` (pure, `src/runtime/failure.ts`) driven by that loop; `FAILURE_CLASSES` is a closed list like the rejection reasons. Retry budgets are counted by replay (`StepView.retryUsage`), never in memory, and a retry is a new attempt in a new workspace from the step's base commit. An attempt whose agent did not end cleanly is classified from `AttemptExit` (`error`, `stopReason`, exit code) and is not verified. A retry after a failed verification issues a new handoff revision whose `evidence` omits the output of hidden tests (`retryEvidence` in `src/runtime/handoff.ts`). Time goes through a `Clock` (`ExecuteRunOptions.clock`): tests that can wait pass `fakeClock()` from `test/helpers/clock.ts` and never really sleep.

Capabilities and reporting (ticket 11): `AdapterDeclaration` (`src/adapters/contract.ts`) is static and complete: transport, model reporting level, login kind, `gracefulCancel`, and an `EnforcementLevel` for every `CapabilityKind` (`read_only`, `write_scope`, `no_external_actions`) and every `NetworkStance` (`deny`, `package_registries`) on every OS (`LevelsByOs`; a platform outside `OPERATING_SYSTEMS` is `none`), all closed lists in `src/protocol/capabilities.ts`. A step lists `capabilities` (each kind once, `require` defaulting to `cooperative`) and a `network` stance (default `deny`, `require` defaulting to `none`); `requestsOf` (`src/runtime/capabilities.ts`) puts them in the handoff (`capabilities`, `network`) and adds the baseline `no_external_actions` (`require: none`, so it is reported and never rejects). `decideHandoff` validates against the declaration of `handoff.to.adapter` (so a reroute is checked against the alternative) for `run.platform` (`ExecuteRunOptions.platform`, default `process.platform`; tests inject another): `resolveCapabilities` returns the `capability_unsatisfiable` reasons (pointers `/capabilities/<i>` and `/network`) and the `AppliedCapabilities` that `attempt_created` records and `AttemptInput.capabilities` hands the adapter. Those levels are the declared ones, read before the agent starts and never from the tool afterwards: reports say so, and only `enforced_by_tool` is ever called enforcement (prompt instructions and ACP permission requests are `cooperative`). The mock declares `cooperative` at most and `none` for the network, and does nothing about what it is told; tests wrap `mockAdapter` with another `declaration` and pass it to `executeRun`'s `adapters`. `AttemptExit.reportedModel` and `.usage` are recorded on `attempt_exited` (`reportedBy` in `src/runtime/run.ts`: a blank model is `unknown`, a usage that `isUsageReport` rejects is not recorded; numbers not reported are null, never 0, never summed or estimated), also for a cancelled attempt if its adapter reported them. Replay reads the new event fields with `?? null`, so ledgers written before them still replay.

Conformance (ticket 12, seam 2): `runConformance(subject, options)` (`src/conformance/run.ts`) is plain data-returning code (no Vitest in `src/`), so a result can be recorded; it drives an adapter through `Adapter.startAttempt`/`exited`/`cancel` only. A `ConformanceSubject` (`src/conformance/subject.ts`) is the adapter plus `provokers`: for each `Scenario` (closed list), the adapter options that make its coding agent do it (the mock's, `src/adapters/mock/conformance.ts`, are scripts). A check with no provoker is `skipped`, never passed; `not_applicable` is a level declared `none`; a result is `outcomeOf` passed only with no failed and no skipped check (else `failed` or `untested`), and `only` runs some checks and records the rest skipped. Only the declared level on the system being checked is tested (`options.platform`): `enforced_by_tool` is probed by an agent that tries to break it, with left-behind state (workspace diff, shared refs, a request to a local listener) as the evidence, after a control run of the same agent with every level recorded as `none` that must break it (else the check is skipped: a probe that breaks nothing shows no enforcement); `cooperative` is checked as accepted only and the detail says it is not enforcement; `declaration:refuses_above_declared` checks the contract's rule that an adapter throws rather than apply a level above its declaration (the mock does, through `this.declaration`, so a test wrapper built by spreading `mockAdapter` is held to its own). Cancel expectations follow `gracefulCancel` and `process.platform` (transport / SIGTERM then `signal` / tree kill on Windows), and the forced-tree check trusts PIDs, not the adapter's `Termination`. `SUITE_VERSION` is bumped when a check is added or made stricter (`test/conformance-matrix.test.ts` pins `CHECK_IDS`); the matrix reads an older pass, or a result lacking any current check, as untested. A subject may set `requestedModel`; a reported model equal to it, with nothing the tool was told to say, is skipped as an indistinguishable echo. A real adapter is refused when `CI` or `GITHUB_ACTIONS` is set (`ConformanceRefusedError`) and needs a tool version (the subject's `toolVersion` or `--tool-version`); the mock records `n/a (mock)`, `mock` comes from its declaration, and `matrixOf` ignores mock results. Results are one JSON file per adapter × OS label in `conformance/results/` (`recordResult`, `readResults`; the mock is recorded only with `--out`), the OS label is `osLabelOf` (`Windows`, `Linux (WSL2)`, `Linux`, `macOS`). `test/conformance.test.ts` runs the mock's full suite and then wraps the mock into deliberately broken adapters (a model echoed from the request, usage with no source or a 0, a cancel that lies, a declaration of `enforced_by_tool` that the agent breaks) with `only`, because a full run starts dozens of processes (about 20 s on Windows); `test/conformance-matrix.test.ts` and `test/conformance-script.test.ts` cover the records, the matrix and `scripts/conformance.ts`. A new adapter ticket adds its subject to `scripts/conformance.ts` and its provokers beside the adapter.

Doctor and init (ticket 13): `src/doctor/tools.ts` is the one table of the three tools (`TOOLS`: command, version args, `LoginProbe`, the adapter name it registers under, `paidAccess`); a ticket that adds a real adapter registers it under that name and its row of `ahp doctor` then shows the declared levels (`levelOn` for this OS), while a tool with no registered adapter shows none, never inferred. `diagnose` (`src/doctor/doctor.ts`) runs only each tool's version command and, where it has one, its own login-status command, through `resolveExecutable`/`launch` from the temp directory with a timeout (`probe`, `src/doctor/probe.ts`: a hung tool's tree is terminated). Login is read as a boolean or an exit code and the rest of the output is dropped; a status AHP cannot read, or a tool without a status command, is `unknown`. No credential, environment variable or config file is read. `usable` (installed, has an adapter, not known logged out) is what `ahp init` casts from (`assignRoles`, pure: preferred tool, else the first usable, else `mock`); `renderWorkflow` builds the reference scenario as an object, runs `validateWorkflow` and writes a plain `export default` module, so an unregistered adapter is refused rather than written. `initWorkflow` never replaces a file. Node's minimum comes from `package.json` `engines`; the git minimum is `MINIMUM_GIT`. `ahp doctor` exits 1 only when Node or git is below its minimum. Tests: `test/doctor.test.ts` (fake tools on PATH from `test/helpers/fake-tools.ts`, which log their argv and print fake credentials) and `test/init.test.ts` (including `ahp run`/`ahp approve` of the generated workflow against a bare remote).

Claude Code adapter (ticket 15; `src/adapters/claude-code/`, user doc `docs/adapters/claude-code.md`): registered as `claude-code` (the name `TOOLS` and `ahp doctor` use), `claudeCode({ model, ... })` names it for a step. One process per attempt: `claude -p --output-format stream-json --verbose --permission-mode dontAsk --tools <named set> --settings <file> --setting-sources project --strict-mcp-config --no-session-persistence`, the prompt (`src/adapters/prompt.ts`, shared with Codex, from the handoff, never the verification command) on stdin; never the Agent SDK, never `--bare` added or removed. `ClaudeStream` (`stream.ts`) is the pure parser: unknown event types and torn lines are ignored; output fields come from `result.structured_output` (`--json-schema` over the step's required fields plus the `reportFields` option); the model from the answers' own `message.model` (not `init`, and not `<synthetic>`: a failed login names none); usage from `result` only, `cache_read_input_tokens` as `cachedInputTokens`, `totalTokens` null, cache writes named in the `source` text, an all-zero block not recorded; errors only from `result` and the assistant message's `error` code (`rate_limit_event` is on healthy runs). Capabilities are declared `cooperative` on every OS and the network stance `none` (ticket 14 decision 7; a shell bypass was observed on Windows): `settings.ts` removes the write tools from `--tools` for `read_only`, writes deny rules (`Bash(git push:*)`, `Bash(gh:*)` ...) and registers `hook.ts`, a standalone `PreToolUse` Node script for the file tools that reads a policy file (workspace, read-only, scope) and exits 2 to block; it also keeps file-tool writes inside the workspace and out of `.git` for every attempt, since an allow rule alone lets `Write` go anywhere (observed). Settings and policy go in a temp directory outside the worktree and are removed when the attempt ends; hook paths are double-quoted with forward slashes. `startAttempt` throws above the declaration (through `this.declaration`) and when `claude` is not on PATH (the runtime then records the attempt `unknown`). Cancel is the process layer's: forced tree kill on Windows. Tests: `test/claude-code.test.ts` runs the adapter against a fake `claude` (`test/helpers/claude.ts`, built on `installFakeTool`) that prints streams captured from the real 2.1.311 (`test/fixtures/claude-code/`, scrubbed), and the hook as a real child; the real `claude` never runs in a test. Because `claude` is now registered, a test that expects no usable tool runs `ahp` with `pathWithoutTools()`. `claudeCodeSubject` (`conformance.ts`) leaves `rate_limited`, `no_model_report` and `no_usage_report` unprovoked, so the suite's outcome is `untested` with those three skipped; run it with `npm run conformance -- run claude-code` (not in CI; unset `ANTHROPIC_API_KEY`).

Codex adapter (ticket 16; `src/adapters/codex/`, user doc `docs/adapters/codex.md`): registered as `codex`, `codex({ model, ... })` names it for a step. One process per attempt: `codex exec --json --sandbox <mode> --config approval_policy="never" [--config windows.sandbox="unelevated"] --ignore-user-config --ignore-rules --cd <workspace> [--model m] [--config model_reasoning_effort=e] [--output-schema <file>] -`, the prompt on stdin; never the Codex SDK, never `app-server`, never `danger-full-access` or a bypass flag (a test asserts it), never `--ephemeral` (the session log is where the model is read). `sandboxFor` (`args.ts`) picks the mode from the **level recorded** for `read_only` (`none` is `workspace-write`, anything else `read-only`), never from the request, so the conformance suite's control run can break the capability; there is deliberately no option for the sandbox, the approval policy or a config override. Declaration: `read_only` is `enforced_by_tool` on win32 only (the suite's probe and control both held there), `cooperative` on darwin and linux (not measured), `write_scope` and `no_external_actions` `cooperative` everywhere (a sandbox mode is workspace-wide and cannot hold a path), network `none` everywhere (a local listener was reached under both modes). `workspace-write` also writes under `%TEMP%`. `CodexStream` (`stream.ts`) is the pure parser: unknown events and torn lines are ignored; only `turn.failed` (or the last non-"Reconnecting..." `error` of a non-zero exit) is a failure, classed from the HTTP status or JSON `code` in its message (401, `model_not_found` and a quota or usage limit `config_auth`, 408/429/5xx `transient`, the rest `agent_error`; the three tool adapters class a quota, usage limit or payment problem `config_auth` since retrying it only spends attempts, seen from Codex as plain text on 2026-10-29); output fields come from the last `agent_message` read as JSON (`--output-schema`); usage from `turn.completed` only, where `input_tokens` **includes** `cached_input_tokens` (the opposite of Claude Code), `totalTokens` and `cost` null, cache writes and reasoning named in `source`, an all-zero block not recorded. The stream never names the model: `session.ts` reads `turn_context.model` from `$CODEX_HOME/sessions/.../rollout-*-<thread id>.jsonl` (newest three day folders, first 200 lines, no other line parsed), and Codex writes it even when no model answered, so `index.ts` reports it only if `stream.answered`; with a requested model it is the same name, so the suite skips `model:reported` as an echo. Cancel is the process layer's. Tests: `test/codex.test.ts` runs the adapter against a fake `codex` (`test/helpers/codex.ts`, `installFakeCodex`, which can write a session log under a test's own `codexHome`) that prints streams captured from the real 0.146.0 (`test/fixtures/codex/`, scrubbed); the real `codex` never runs in a test and nothing reads the real `~/.codex`. `codexSubject` (`conformance.ts`) provokes a failure with an effort the model refuses (`minimal`), a missing login with an empty `codexHome` it creates, and `writes_when_read_only` by telling the agent the limit is under test; it leaves `rate_limited`, `no_model_report` and `no_usage_report` unprovoked, so the outcome is `untested`; run it with `env -u OPENAI_API_KEY -u CODEX_API_KEY npm run conformance -- run codex` (not in CI).

OpenCode adapter (ticket 18; `src/adapters/opencode/`, user doc `docs/adapters/opencode.md`): registered as `opencode`, `opencode({ model, ... })` names it for a step. The first ACP adapter, and the reason `launch` has a `duplex` mode (`LaunchOptions.duplex`: stdin stays open and is `LaunchedProcess.stdin`; the rest of the process layer is unchanged). One process per attempt: `opencode acp --pure --cwd <workspace>` with `OPENCODE_CONFIG_CONTENT` (the step's permission rules, inline, so no worktree file can weaken them) and `OPENCODE_DISABLE_CLAUDE_CODE`/`OPENCODE_DISABLE_EXTERNAL_SKILLS` (the user's `~/.claude` skills otherwise became commands, observed). `AcpConnection` (`src/adapters/acp/connection.ts`) is the whole client: JSON-RPC lines, a message with a `method` is the agent's request or notification whatever its id (the agent numbers its requests from 0 like the client), and an agent request nothing handles is answered `-32601`, never left waiting. `index.ts` runs one conversation: `initialize` (no client capabilities), `session/new`, `session/set_config_option` for the model only when one is requested (a refusal fails the attempt as `config_auth` and no prompt is sent: the default model never runs in its place), one `session/prompt`, then ends stdin, which is what makes an ACP agent exit (a process that has not exited 10 s later is terminated). A failed turn leaves exit code 0, so `AcpTurn` (`turn.ts`) records the error itself (`classify` reads the message; `redacted` removes `sk-` keys and bearer tokens, the ledger being public); `cancelled` is no stop reason and its zero usage is not recorded. Usage is the prompt result's (`inputTokens` excludes `cachedReadTokens`, `totalTokens` is input + output + thought + cached read, measured), cost only from a `usage_update` above zero (OpenCode reports 0 for a model it does not price); the reported model is `opencode export <session>`'s last assistant `providerID/modelID`, run after the exit and only for a turn in which the model did something, never the session's `configOptions` (a selection). OpenCode has no structured output, so the fields are asked for as one JSON object that is the whole final message (`promptFor`'s `reportHow` argument) and read from it, bare or fenced. Declaration: `transport: acp`, `gracefulCancel: true`, `modelReporting: enumerable`, every capability `cooperative` and the network `none` on every OS; `policy.ts` is the rules (`edit: deny` for read-only, `edit: ask` for every other step, `bash` deny patterns for `git push`, `git update-ref` and `gh`) and `acp/permissions.ts` has `decide`, which answers a `session/request_permission` by the policy with `allow_once` or `reject_once` (never `allow_always`: it would outlive the attempt in the user's rules; the model is not looked up for a cancelled attempt). Cancel is the transport's: `session/cancel`, wait for the turn, end stdin; the process layer kills the tree only if that does not clear it. Tool-call log (the first adapter to keep one): `AttemptInput.toolCallLog` is a file the runtime owns (`toolCallLogPath`, `<runs>/<run>/tool-calls/<attempt>.jsonl`) where the adapter appends a `ToolCallLogEntry` (kind, title, status, workspace-relative paths, AHP's permission answer; never input or output) as each call happens, because an `unknown` attempt never reaches `exited`; `buildRecoveryReport` reads its last 100 lines (`RecoveryReport.toolCallLog` is `null` for an adapter that wrote none) and `ahp recover` prints them. The Linux/macOS tree termination (`terminateGroup`, `src/process/tree.ts`) reads the root's descendants by parent PID (`descendantsOf`, `ps`, with start times) before it sends anything and kills those the group did not hold (OpenCode's shell commands start their own session, observed on Linux, so the group alone reported a tree gone that was running). Evaluation core (ticket 20; `src/evaluation/`, user doc `docs/evaluation.md`; `ahp eval <suite-file> [--out <dir>] [--json]`, `runEvaluation` in the SDK). Ledgers live at `<git common dir>/ahp/runs/<run>/ledger.jsonl`; snapshots are pinned under `refs/ahp/snapshots/<run>/<attempt>`. Every event carries `seq`, `prevHash` and `hash` (SHA-256 over the event's canonical JSON without `hash`, `src/ledger/chain.ts`); readers check the whole chain and throw `LedgerCorruptError` rather than derive state from a broken one, and leave out a torn tail (a last line without its newline, or not JSON). `LedgerWriter` (`src/ledger/writer.ts`) holds `ledger.lock` beside the ledger from `create`/`open` until `close`: created exclusively, it records host, PID and process start time, and a lock whose process is gone is reported as stale (`src/ledger/lock.ts`); only `ahp recover` takes one over (`LedgerWriter.open` with `takeOverStale`), recording the old owner in `run_resumed` (the stale lock of a run that has ended is removed with no event, `clearStaleLock`), and `close` removes the lock only while it still names its writer. `LedgerWriter.open` truncates a torn tail and records `ledger_truncated`. File opens, reads and unlinks retry `EBUSY`/`EPERM` briefly (`whileBusy`); writes never retry. Worktrees live outside every repository at `<AHP_HOME>/worktrees/<run>/<attempt|verification>` (per-user state dir by default, see `src/runtime/paths.ts`) so Node resolution and config lookups from a worktree can never reach the user's checkout. Tests set `AHP_HOME` to a temp dir in `test/helpers/setup.ts`.

## Direction in brief

AHP (Agent Handoff Protocol and LLM Evaluation) makes handoffs between AI **coding agents** explicit, verifiable and measurable, and evaluates whether that improves real task outcomes.

- Release 1 targets three coding-agent CLIs: **Claude Code, Codex CLI, OpenCode** (Gemini CLI dropped 2026-10-30), combinable in one workflow, each via a dedicated adapter. Core has no provider-specific logic.
- **TypeScript + Node.js**, cross-platform (Windows, macOS, Linux). Publish a support matrix; never claim an adapter works on an OS it was not tested on.
- Components: protocol (versioned spec), SDK, adapters, runtime, append-only event-sourced ledger, evaluation engine, `ahp` CLI.
- Out of scope for release 1: web platform, visual editor, serving/downloading models, inference-engine benchmarking (Ollama/vLLM/SGLang/TensorRT-LLM), reflection/simulation, direct model-provider connections.
- Positioning: ACP is a candidate transport for driving agents; AHP data shapes map to A2A where semantics match, with AHP-specific semantics as an A2A extension profile. Do not invent a competing general-purpose protocol.

## Rules the design depends on

- **Core hypothesis:** structured validated handoffs (with runtime-checked acceptance) beat a single agent and a plain-text pipeline on verified success and context loss. Evaluation conditions C0–C3 (see design doc §7). A negative result is legitimate.
- **Never fabricate results.** Mock adapter output is never evidence. Report usage/cost only where an integration reports it, labelled with its source. Report models as requested vs reported; never claim to discover subscription entitlements.
- **Success = verification passes**, never an agent's self-report.
- **Keep the four concerns separate:** run/step state, handoff validation, attempt state, result verification.
- **`unknown` attempt outcomes are never retried automatically**; they go to `needs_recovery` under an explicit recovery policy: `manual` (default), `adopt` or `abort`. In evaluation they are harness incidents.
- **Verification runs in a fresh verification worktree**, never the agent's live worktree; there is no "Tester" agent.
- **Only AHP performs external actions** (push/PR/merge); no deploy in release 1.
- **A git worktree is workspace isolation, not a security boundary.** Each applied capability carries an enforcement level (`enforced_by_tool` / `cooperative` / `none`). Never describe prompt instructions or ACP permission requests as enforcement.
- AHP never stores provider credentials; adapters use each tool's own login.
