# 04: Failure classes, retries and handoff revisions

**What to build:** When an attempt fails, the runtime classifies it and retries within budget. A failed verification is retried with its evidence attached in a new handoff revision; a transient failure is retried with backoff under the same revision. Exhausted budgets reroute when configured, otherwise the step fails.

**Blocked by:** 02, 03

**Status:** done

**Model:** Sonnet 5.5 · xhigh

- [x] Failure classes: `rejected`, `config/auth`, `transient`, `agent_error`, `verification_failed`, `inconclusive`, `unknown`
- [x] `rejected` and `config/auth`: no retry; `config/auth` surfaced to the user
- [x] `agent_error` + `verification_failed` share a default budget of 2 retries per step; configurable
- [x] `transient` has a separate default budget of 5, exponential backoff, capped total wait
- [x] `inconclusive`: validator re-run once, then escalate
- [x] Same-input retry = new attempt under the same revision; changed-input retry = new revision, old one `superseded`
- [x] Idempotency key is (handoff ID, revision, attempt ID); every retry gets a new workspace
- [x] Reroute to an alternative adapter under the same contract, off by default
- [x] `unknown` is never retried (handling arrives in 06)

## Implementer notes

- Make time injectable (a clock and a sleep function passed to the runtime) so backoff tests run instantly; tests must never really sleep.
- Write one test per failure class using a mock script that produces it, asserting the resulting attempt count, revisions and final step state from the ledger.
- Classification is a pure function from an ended attempt (exit code, stop reason, adapter-reported error kind, verdict) to a failure class; test it as a table.
- Budgets are counted from ledger events by replay, never from in-memory counters, so a restart sees the same remaining budget.

2026-10-25, implementation notes. The ticket left several shapes open; these are the choices made, so ticket 05 and later can build on them or reopen them.

**Four decisions the tickets left to me (veto any of them):**

- **A non-zero exit is not verified.** This replaces ticket 01's placeholder deliberately. An attempt whose agent did not end cleanly (non-zero exit or a signal, a stop reason of `refusal`, `max_tokens` or `max_turn_requests`, or an error its adapter reported) is classified from how it ended, its workspace is still snapshotted, and it is never verified: it has no finished result to check, and `exited(error)` with a passing verification would contradict itself. The classifier's `verdict` input is therefore null for such attempts. A passing workspace behind a crashed agent does not rescue the step (tested).
- **What a retry may show of hidden tests.** Ticket 03 handed this over. The handoff revision's `evidence` carries only the failing parts of the verification: a failing command's exit code and the last 8 KiB of its output, the required output fields left out, and the changed paths that violated a protected path. When the step declares `hiddenTests`, the command's output is withheld (`output: null`, exit code kept), because the command runs them and their output can quote their expectations. The list of protected paths is never shown, since it holds the hidden tests' paths; only the paths the agent itself changed that were protected are named. The ledger keeps the full evidence for the person reading it. A step with hidden tests therefore retries on little more than "the hidden tests failed (exit code 1)", which weakens C3's retry on such steps; a task author who wants richer feedback should put it in a visible check. If you want a per-step opt-in to show hidden-test output, it is one flag on `VerificationDefinition` and a branch in `retryEvidence`.
- **"Escalate" for `inconclusive`.** No approval-gate machinery exists before ticket 09, so escalation is: one validator re-run on the same snapshot (no new attempt, nothing spent), and if that is inconclusive too the step fails with class `inconclusive` and `ahp run` says the user must fix the validator or its environment. A re-run that finds the work failing is an ordinary `verification_failed` and follows the retry path.
- **A reroute starts the alternative agent on fresh budgets.** The spec says the shared budget is "2 retries per step" and does not say what a reroute does to it. I read the budget as per agent: a reroute resets the retry counters and the transient wait, so the alternative gets a fair try, and a step is rerouted at most once. With the defaults a rerouted step makes at most 3 attempts with the first agent and 3 with the alternative. The literal "per step" reading is stricter (the alternative would get one attempt and no retries, 4 attempts in all, which costs less under real usage); switching to it is deleting the reset in `replay.ts` and the `rerouted` guard in `decideAfterFailure`'s caller. The first agent's spend stays in the ledger and the attempt list; `StepView.retryUsage` shows only the current agent's.

**Shapes:**

- **Declaration** (`StepDefinition`, `src/protocol/index.ts`): `retry: { budget, transientBudget, backoff: { initialMs, factor, maxTotalMs } }` and `reroute: AgentRef`, all optional and validated statically (non-negative integers, waits of at most 2^31-1 ms because a longer timer fires at once, `factor` at least 1, the alternative held to the same adapter and option checks as `agent`, adapter and option messages prefixed `reroute:`). Defaults: budget 2, transientBudget 5, backoff 2 s × 2 per retry, total wait capped at 120 s. A transient retry whose wait would take the step past the cap is not made: that counts as the budget being spent.
- **Failure classes** are `FAILURE_CLASSES`, an `as const` list; the identifier is `config_auth` (the ticket writes `config/auth`).
- **Policy is two pure functions** in `src/runtime/failure.ts`, exported from the SDK and tested as tables: `classifyAttempt` (adapter error first, then stop reason and exit code, then verdict) and `decideAfterFailure` (retry same input, retry with evidence, re-run the validator, reroute or stop). `rejected` and `unknown` are never produced by classifying an ended attempt, so their "never retried" rule is only tested in the decision table: the mock cannot produce `unknown` until ticket 06.
- **Adapter contract:** the spec lists "classification of an ended attempt" under the adapter. Here the adapter reports what it saw (`AttemptExit.error: { kind, message }`, kind one of `config_auth | transient | agent_error`, and `AttemptExit.stopReason`) and the core maps it, so the table lives in one place. `STOP_REASONS` leaves out ACP's `cancelled`: cancellation is ticket 07. `attemptNumber` counts every attempt of the step across agents; the mock picks its script by that number, so a reroute alternative's scripts start after the first agent's attempts (tests pad them).
- **Ledger:** new events `attempt_failed` (the class, recorded once the verdict is final) and `retry_scheduled` (`change: none | evidence | reroute`, `delayMs`, recorded before the wait and before the new revision or attempt); `attempt_exited` gained `stopReason` and `error`. The successful path's events are unchanged. Derived state gained `AttemptView.failureClass | stopReason | error | earlierVerifications` and `StepView.retryUsage` (retries, transient retries, transient wait, rerouted), counted by replay from `retry_scheduled`; the runtime reads it from replay, so a restart sees the same budget. A reroute resets the counters for the alternative. Replay now also refuses an attempt ID used twice (the idempotency key), an attempt on a step that is not `ready`, a failure class its attempt's record contradicts, a retry on a finished step, for an attempt that is not the failed last one, with a change its class does not allow, or a second reroute, and a second verification of anything but an inconclusive first one (once). Those rules are tested by cutting a finished ledger after an `attempt_failed` and appending hand-made events (`truncateLedgerAfter` in `test/helpers/ledger.ts`, valid only until ticket 05 adds the hash chain).
- **Handoff:** `evidence` is a required array on the revision (empty for revision 1, and revision 1 with evidence is `schema_invalid`), with kinds `test_output`, `required_output_fields` and `protected_paths`. `schemas/` is regenerated; `schemaVersion` stays `0.1.0` while the protocol is 0.x. Ledgers written before this ticket hold handoffs without `evidence`: they still replay, but `validateHandoff` would reject those documents. A revision is the previous document with its input changed (`reviseHandoff`): same handoff ID, base commit, contract, context and artifacts; a reroute also names the alternative as `to`. When the failed attempt taught nothing (a reroute after agent errors) the revision keeps the evidence the step already had. Protected-path violations in evidence are plain strings, not checked against the repository-path rules, so a file name that is legal on the agent's OS cannot turn a retry into a rejected handoff.
- **Retry kinds:** `agent_error` and `transient` retry with the same input (nothing new to attach), `verification_failed` with evidence, an exhausted budget with a reroute. `config_auth`, `rejected`, `inconclusive` and `unknown` are never rerouted.
- **Time:** `Clock { now, sleep }` through `ExecuteRunOptions.clock` and `RunWorkflowOptions.clock`; the ledger's timestamps come from `now`. The step's total wait is the sum of recorded delays, not elapsed time. `fakeClock()` in `test/helpers/clock.ts` records sleeps and advances time, and no test really sleeps: the CLI tests cannot inject a clock, so none of them involves a transient wait.
- **CLI:** `ahp run` streams `failed: <class>`, the retry (or reroute) with its wait, and, for a failed step, one line saying what was done about it (`not retried: <adapter message>` for `config_auth`, `escalated: ...` for `inconclusive`, `retry budget spent`). `ahp inspect` shows each attempt's failure class, stop reason and adapter error, earlier verifications that were re-run, and what a step spent.
- **Existing tests:** steps that fail by design and script one attempt now set `retry: { budget: 0 }` in their helpers (`run`, `verification`, `handoff` and CLI tests), because the default budget would ask the mock for a script it does not have. The mock deliberately does not repeat its last script, so a retry that was not meant to happen fails loudly. I checked by hand that removing the wait cap, the validator re-run or the hidden-output withholding each makes a test fail.
- **For tickets 06 and 08:** `attempt_failed` and its replay check (`ATTEMPT_SHOWS` in `src/ledger/replay.ts`) accept only an attempt that has `exited`, and never record `unknown`; 06 will have to relax that and decide what `retry_scheduled` means after an adopted or aborted `unknown` attempt. Replay refuses `retry_scheduled` on a step that already succeeded, which 08's send-back (a `succeeded` step back to `ready`) cannot use as it stands; review findings and an approver's reason also need a new `HandoffEvidenceSchema` kind, which is a protocol change (`npm run schemas`). Send-back should spend the same `retryUsage.retries` and go through `decideAfterFailure` as a `verification_failed` rather than grow a second budget.
- **Not done:** thrown adapter failures (a spawn error, an unreadable mock report) still propagate out of `executeRun` mid-attempt, as before; they are ticket 06's `unknown`. No attempt timeout, so `timed_out` is never produced, and a backoff wait cannot be interrupted (ticket 07). No jitter in the backoff. `diff_scope` and `validator_error` evidence are never shown to the agent. Replay checks that a retry is allowed for its class but not the numeric limits, which live in the workflow definition rather than the derived state; the runtime enforces them from replay-derived usage.
